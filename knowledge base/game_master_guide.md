# Game Master Guide

How to change the way the daily game plays without touching code, what each
control actually does, and how to tell whether a change helped.

Written for both audiences: a person tuning the game, and an agent asked to
change or extend these controls. Sections 1–6 are the human path. Section 7 is
the map an agent needs. Section 8 is what will surprise you.

---

## 1. Where

**`/admin/game-settings`** — linked from the admin dashboard as *Game Settings*.
Requires `profiles.is_admin = true`; everyone else gets a 404, which is
deliberate (it hides that the admin area exists at all).

Changes take effect on the **next page load**. There is no deploy, no build, and
no cron wait.

| Layer | Where it lives | Editable at runtime? |
| :--- | :--- | :--- |
| Game-master policy | `game_settings` table, key `daily_hint_policy` | **Yes** — the admin page |
| Player preference | `profiles.settings` / localStorage | By the player, in the info screen |
| Experiment override | PostHog `dailygame-auto-hint-level` | Yes — the PostHog console |
| Compiled default | [`src/lib/gameConfig.ts`](../src/lib/gameConfig.ts) | No — needs a deploy |

The compiled defaults are the floor. If the table is missing, unreachable, or
full of nonsense, the game plays exactly as it did before these controls
existed. **You cannot brick the daily game from this page.**

## 2. What you control

### How words open

| Setting | Values | What it does |
| :--- | :--- | :--- |
| **Start level** | 0–3 | The hint level a word already carries when the player reaches it. `0` gives nothing away. |
| **Applies to** | first word / every word | Whether the start level covers the whole chain or only the first word the player faces. |
| **Charge for the free hint** | on / off | Whether a hint the player never asked for still costs them points. |

Levels: **1** = first letter and length · **2** = scramble (first letter pinned,
most of the rest shown but shuffled) · **3** = the AI clue, which usually gives
the answer away.

### The automatic ladder

| Setting | Values | What it does |
| :--- | :--- | :--- |
| **Automatic hints** | on / off | Master switch. Off means hints only ever arrive when the player asks. |
| **Delays are** | gaps / offsets | How the three delay numbers are read. See §3. |
| **Progression** | ladder / jump | `ladder` climbs 1 → 2 → 3. `jump` sends every hint straight to the AI clue. |
| **Each rung** | auto on/off, 0–600s | Per hint level: whether it fires on its own, and after how long. |

### Reach and blast radius

| Setting | Values | What it does |
| :--- | :--- | :--- |
| **Scope** | default / force | Whether the policy binds every player or only those who never set their own preferences. See §4. |
| **When these settings change** | keep / restart | What happens to someone already mid-game. See §5. |

## 3. Gaps vs offsets

The same three numbers mean two different things, and this is the control people
misread most often.

With delays of **15 / 30 / 60**:

| Mode | Reading | First letter | Scramble | AI clue |
| :--- | :--- | ---: | ---: | ---: |
| **Gaps** (`per-rung`) | wait *between* hints | 15s | 45s | 105s |
| **Offsets** (`cumulative`) | measured from the word opening | 15s | 30s | 60s |

**Offsets is usually what you want.** "Every hint is out by one minute" is a
sentence you can reason about. "The last hint lands at 105 seconds" is one you
have to compute.

Offsets has a second property that matters: a player who takes a hint manually
does **not** push the rest of the schedule back. The promise holds regardless.

The admin page draws the resulting timeline underneath the rung editor. It is
generated by running the real scheduler, so it cannot drift from what players
actually get — trust it over your own arithmetic.

Setting every delay to **0** gives the whole ladder away at once, spaced half a
second apart so the player can watch the levels step up.

## 4. Scope — read this before you tune anything

**`default`** seeds only players who have never touched their own hint settings.
**`force`** overrides everyone.

The trap: if you have ever opened the daily game's info screen, you have
preferences saved. Under `default`, your own account will **not move** when you
change a delay, and the page will look broken.

- **Balancing?** Use `force`. You want to see what you are shipping.
- **Launching?** Switch to `default` and hand control back to players.

Settings players cannot express for themselves — start level, progression,
stagger, charging — are always the game master's, whatever the scope.

---

## 5. How a change reaches players

Every save bumps **`game_settings.revision`**. That number is stamped onto each
player's saved game and onto every result they record.

A player's game lives in localStorage. By default a change does **not** disturb
someone already mid-game — they finish the day on the configuration they
started with. That is the `keep` setting, and it is why a change can look like
it did nothing.

Set **When these settings change → restart** if you want a change to land
immediately. It discards in-progress games for anyone on an older revision.
Fine while you have almost no players; rude once you do.

## 6. Telling whether it helped

The **How it has played** table sits below the settings on the same page. One
row per revision, newest first, over the last 30 days.

| Column | Means |
| :--- | :--- |
| Plays | One per browser per day |
| Finished | Share who completed the chain |
| **Reached** | How many words they got through, solved or not — **where they stop** |
| Solved | How many they actually got |
| Hints/word | Hints taken per word reached |
| Time/word | Attention per word (tab-hidden time excluded, walked-away plays capped) |

Rows are grouped by **revision, not by date**, and that distinction is the point:
players who cached their game keep playing the old configuration for the rest of
the day, so a date range mixes both. The revision travels with the play.

**Reached is the number to watch.** Completion rate tells you whether the game
is winnable; reached tells you where it loses people.

A revision labelled `code defaults` (revision `0`) means the settings table
could not be read. `unattributed` rows predate the tracking column.

The same `settings_revision` is attached to the `daily_game_entered`,
`daily_word_solved` and `daily_game_completed` PostHog events, so the
[dashboard](daily_game_performance_dashboard.md) can break down by it too.

### A workable loop

1. Change one thing. Note the revision the page reports.
2. Leave it for enough plays to mean anything. At this game's current traffic
   that is days, not hours.
3. Compare its row against the one above it.
4. Keep it, or set the previous values back — which creates a *new* revision
   rather than reusing the old one, so the history stays honest.

## 7. For agents working on this

### Where the logic lives

| Outcome aggregation | [`src/lib/daily/outcomeStats.ts`](../src/lib/daily/outcomeStats.ts) |
| The countdown itself | [`src/components/daily/useAutoHint.ts`](../src/components/daily/useAutoHint.ts) |

| Scoring, including free hints | [`src/lib/daily/dailyScoring.ts`](../src/lib/daily/dailyScoring.ts) |

Every pure module above has a colocated `.test.ts`. Behaviour changes go in the
pure module with a test, not in the hook or component.

### The policy

```ts
type DailyHintPolicy = {
  startLevel: number;                                 // 0-3
  startLevelAppliesTo: 'first-word' | 'every-word';
  chargeForStartLevel: boolean;
  autoEnabled: boolean;
  rungs: [HintRung, HintRung, HintRung];              // to L1, L2, L3
  progression: 'ladder' | 'jump';
  stagger: 'per-rung' | 'cumulative';
  onRevisionChange: 'keep' | 'restart';
};

type HintRung = { auto: boolean; delaySeconds: number };  // 0-600
```

### Invariants — do not break these

1. **`DEFAULT_HINT_POLICY` reproduces pre-policy behaviour exactly.** Asserted by
   test. It is what makes adopting the policy a refactor rather than a silent
   gameplay change.
2. **`parseHintPolicy` is total.** Never throws, never returns a partial object,
   clamps per field. It is the boundary between a hand-editable jsonb column and
   the game loop.
3. **Reads degrade, never fail.** A missing table, missing row, or malformed blob
   falls back to the compiled defaults and logs which migration is missing.
4. **`game_settings` is world-readable.** Guests play the daily game with no
   session, so anon must be able to read it. **Never put a secret in this table.**
5. **Writes never go through the client.** RLS has no write policy at all; the
   API route uses the service role after an `is_admin` check. That check *is* the
   authorisation.
6. **Revision 0 ≠ null.** `0` means "played against the compiled defaults", which
   is a real answer. `null` means the column did not exist yet.
7. **The timeline preview runs the real scheduler.** Do not re-derive the timings
   for display — a preview that can drift is worse than none.

### Adding a setting

1. Add the field to `DailyHintPolicy` and to `parseHintPolicy` (with a clamp and
   a per-field fallback), plus a test.
2. Give `DEFAULT_HINT_POLICY` the value that preserves current behaviour.
3. Consume it where the behaviour lives — the pure module, not the component.
4. Add a control to `GameSettingsForm.tsx`.
5. Document it in §2 here.

No migration is needed: the column is a single jsonb blob.

## 8. Things that will surprise you

- **You change a delay and nothing happens to your own account.** Scope is
  `default` and you have your own saved preferences. See §4.
- **You change a setting and nothing happens to anyone.** They are mid-game on
  the old revision. See §5.
- **Raising the start level quietly deflates every score.** A pre-given hint is
  charged for unless you turn *Charge for the free hint* off — and scores then
  stop being comparable with everything recorded before the change either way.
  Decide which you want *before* collecting a week of data.
- **The player's slider flattens your ladder.** The info screen has one delay
  control and the policy has three. A player who touches it sets all three rungs
  to the same value. Under `force` they cannot.
- **A decreasing offsets schedule bursts.** `30 / 10 / 60` leaves the second
  target already in the past, so it fires immediately after the first. This is
  left as-is rather than silently rewritten; the timeline preview shows it.
- **Turning a rung's auto off stops everything past it.** The ladder halts there
  until the player asks for a hint. The timeline marks this "manual only".
- **`jump` makes the intermediate rungs unreachable** — every hint goes straight
  to the AI clue, so their delays stop mattering.

## 9. Operational

Both migrations are **written but must be applied by hand** (the Supabase MCP is
read-only):

| Migration | Adds |
| :--- | :--- |
| `20260822140000_create_game_settings.sql` | `game_settings`, `game_settings_history` |
| `20260823090000_add_settings_revision_to_daily_results.sql` | `daily_results.settings_revision` |

Until they are applied, everything keeps working: the game runs on compiled
defaults, results record without attribution, and both the logs and the admin
page say so and name the file to apply. After applying, regenerate
`src/types/database.types.ts` and replace the hand-written `GameSettingsRow` in
[`src/types/app.ts`](../src/types/app.ts) with the generated alias.

Every save also appends to `game_settings_history` (key, value, scope, revision,
who, when) — service-role only, which is where "what changed on the 14th" is
answered.
